# 工具设计原则

## 说明文档就是功能

在普通后端里，函数的 docstring 是写给人看的，写不写都能运行。
在 Agent 里，工具的描述会变成 `description` 直接送给模型，
**它决定模型会不会在该用的时候用这个工具、参数填得对不对。**

同一个工具，两种写法：

- 差：「查询天气」
- 好：「查询指定城市当天的天气。当用户问到气温、下雨、湿度、穿衣建议时使用」

后者的命中率明显更高。措辞影响行为，这是 Agent 开发与普通后端很不一样的地方。

## 参数设计

- **必填参数越少越好**。每多一个必填项，就多一个模型填错的机会
- **用枚举代替自由文本**。`unit: celsius | fahrenheit` 比 `unit: str` 可靠得多
- **加格式约束**。论文 id 用正则限制成 `p\d{3}`，能在入口就拦住编造的 id
- **参数说明要带例子**。`city: 城市名，如 北京` 比 `城市名` 好

## 失败的处理

工具内部失败分两类，处理方式相反：

| 类型 | 做法 | 例子 |
|---|---|---|
| 业务性失败（正常的空结果） | 返回人话，不抛异常 | 查不到这个城市、搜不到相关文档 |
| 编程性/环境性错误 | 抛异常，由执行层统一捕获 | 除零、类型错、权限不足 |

原因：读工具输出的是模型。返回「暂无该城市数据」，
模型会理解成"这个查询没结果"，可能换个方式再试；
抛出 `ValueError` 堆栈，模型容易理解成"工具坏了"直接放弃。

## 返回值的结构

统一成 JSON，且明确区分成功与失败：

```json
{"ok": true, "result": "..."}
{"ok": false, "error": "invalid_args", "message": "参数不符合要求", "problems": [...]}
```

错误码要可枚举（`unknown_tool` / `invalid_json` / `invalid_args` / `tool_error`），
方便统计"哪类失败最多"。

## 幂等性

写操作类工具要考虑重复执行。模型在失败重试时，很可能把同一个操作发两遍。
转账、发邮件、删文件都要带幂等键，或者在工具内部做去重。

## 返回值的大小

工具返回值会进入上下文，**必须限制长度**。

一个搜索工具返回 10 篇文档全文，一次就是几千 token，
跑 5 轮就能把预算烧光。正确做法是返回摘要 + id，让模型按需读取详情。
