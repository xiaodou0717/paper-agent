# 文档切分策略

## 一句话定位

切分决定了检索的**上限**——切错了，后面再好的检索也救不回来。

## 为什么必须切

三个原因：

1. **embedding 有长度上限**，超长会被截断，尾部信息丢失
2. **检索粒度**：整篇文档一个向量，命中后你要么全塞进去（太长），要么再切（多此一举）
3. **精确性**：一块只讲一个点，召回的相关度才高

## 三种切法

**一、固定长度**

每 500 字符一刀，块间重叠 50 字符。

优点：简单、可控、快。
缺点：**会在句子中间切开**，把"因为……所以……"劈成两半。

**二、按结构切**

按 markdown 标题切，每节一块。

优点：语义完整，符合人的阅读习惯。
缺点：节的长短不可控（有的 200 字，有的 3000 字）。

**三、语义切分**

用 embedding 判断相邻句子的相似度，在"话题转折"处切。

优点：块内主题最集中。
缺点：慢、贵、结果不稳定。

## 实践中的组合

大多数系统用的是**结构优先 + 长度兜底**：

```
先按标题切 → 如果某节超过 800 字，再按段落切 → 如果段落还超长，按句号切
```

这样既保住了语义边界，又保证了块的长度可控。

## 重叠（overlap）的作用

块之间留 10%-20% 的重叠，目的是**别让一个完整的论述被切断**。

比如"三种记忆"这段被切在第二段中间，
下一块的开头保留上一块的结尾，检索命中任何一块都能看到完整上下文。

代价是索引变大、可能召回重复内容。**重叠不是越多越好，15% 是个常见起点。**

## 常见误区

**一块一个固定字符数，不看内容**

代码块被从中间切开，检索回来的代码是残缺的，模型看到会一脸懵。

**切完不检查**

抽 20 个块人工看一眼：有没有从中间断开的、有没有一整块都是标题的。
这个检查十分钟，能避免后面几周的困惑。
