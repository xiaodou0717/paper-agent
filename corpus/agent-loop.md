# Agent Loop 的基本结构

## 五步循环

一个 Agent 的运行本质是一个循环，每一轮做五件事：

1. **调用模型**：把完整对话历史和可用工具列表发给模型
2. **判断是否要用工具**：看返回的 `finish_reason` 是 `tool_calls` 还是 `stop`
3. **解析工具意图**：从 `tool_calls` 里取出工具名和参数（可能有多个）
4. **执行工具**：查注册表、校验参数、执行、捕获异常
5. **回填结果**：构造 `role="tool"` 的消息，`tool_call_id` 必须与调用一一对应

做完第 5 步回到第 1 步，直到第 2 步判断为"不需要工具"。

## 各部分的分工

- 编排层（loop）决定"什么时候执行、执行完干什么"
- 工具层（registry + tools）只负责"给什么参数就执行什么"

这个分层带来一个直接好处：新增工具时不需要改 loop 的代码。
工具层不知道有循环，循环层不知道有哪些具体工具。

## 终止条件

只靠"模型自己说完了"是不够的，必须有三道护栏：

- **最大步数**：防止模型反复调工具、绕圈子
- **token 预算**：防止每轮都正常但总成本失控
- **时间上限**：防止工具或网络挂起导致无限等待

三者防的是不同的故障，不能互相替代。

## 检查点的位置

预算类检查必须放在"发起下一次请求之前"。
因为发起请求这个动作本身就要花钱，放在响应之后检查等于先花了再判断。

代价是它拦不住"正在跑的那一轮"：检查发生在两轮之间，
所以实际耗时或花费总会略微超过上限。这是这类检查的固有边界。

## 常见错误

- 只看 `content` 是否为空来判断循环是否结束。模型要调工具时 `content` 是空字符串，
  必须看 `finish_reason`
- 用 `tool_calls[0]` 只取第一个调用。一次可能返回多个，漏掉的会导致请求被拒绝
- 回填时 `tool_call_id` 写错或漏写。服务端会校验配对关系
- 把"不是 tool_calls"当成成功。协议里还有 `content_filter` 等取值，
  它们表示模型没有正常输出
