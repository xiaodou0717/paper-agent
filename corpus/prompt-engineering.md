# 提示词工程

## 一句话定位

提示词工程解决"**怎么问**"，上下文工程解决"**给它看什么**"。两者不能互相替代。

## 三个真正有效的原则

**一、说清楚"输出长什么样"**

不要写"请详细分析"，要写"用三个要点回答，每点不超过 30 字"。
格式约束是最省 token 的优化——它同时减少了输出长度和返工次数。

**二、给一个例子，胜过十句描述**

模型对"示例"的敏感度远高于"规则"。一个 20 字的例子，
效果通常好过一段 200 字的格式说明。

这叫 few-shot，但重点不是"几个"，而是"**例子和真实输入有多像**"。

**三、把否定句改成肯定句**

```
❌ 不要用 markdown、不要加解释、不要重复问题
✅ 直接输出 JSON，第一个字符是 {，最后一个字符是 }
```

否定句要求模型"先想到那个行为，再抑制它"，
而肯定句直接给出目标行为。后者成功率明显更高。

## 常见误区

**堆砌形容词**

"请你作为一名资深的、专业的、经验丰富的专家，非常仔细认真地分析……"

这些词对输出质量几乎没有影响，但会占用上下文。
**模型不需要你恭维它。**

**把规则写成一长串 if-else**

提示词不是代码。二十条细则里，模型通常只能稳定遵守前几条。
真想约束行为，用工具校验或 response_format，别指望提示词。

## 一个判断标准

**如果这条规则"违反了你一定能发现"，就值得写进提示词；
如果"违反了也不一定看得出来"，就该用代码校验。**

提示词管"倾向"，代码管"底线"。
