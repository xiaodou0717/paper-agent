# Agent 的评测方法

## 为什么不能靠"看起来对"

Agent 的输出是开放式的，同一个任务可能有多条正确路径。
如果只靠人工看几个例子，会出现两个问题：

- 抽样太少，看不到长尾失败
- 判断标准不一致，今天觉得可以，明天觉得不行

## 三层评测

### 1. 组件级

单独测工具、提示词、解析逻辑。速度快、定位准，
但测不出"组件都对、组合起来错"的问题。

### 2. 端到端

给定输入，看最终输出是否符合预期。更接近真实场景，
但失败时不知道坏在哪一步。

### 3. 轨迹级

检查中间步骤，而不只是最终答案。
比如：该调工具时有没有调、调了几次、参数对不对、有没有绕路。

轨迹级评测是 Agent 特有的。普通 API 只看输入输出，
Agent 还要看"过程合不合理"——因为过程决定成本和稳定性。

## 判定方式

- **精确匹配**：适合有唯一答案的抽取任务
- **规则校验**：用正则、JSON Schema、数值范围检查
- **LLM 作为裁判**：适合开放式回答，但要防止裁判偏好长答案
- **人工抽检**：校准用，不能作为主要手段

关键点：**判定标准要写进代码，而不是记在人脑子里。** 否则无法复现。

## 必须记录的指标

- 成功率（按 `stop_reason` 分类统计，区分"答错"和"没答完"）
- 平均步数、平均 token、P95 延迟
- 工具调用次数与失败率
- 失败样本的完整轨迹

## 失败的分类比通过率更有用

通过率 70% 这个数字本身信息量很低。有用的是：
剩下的 30% 里，多少是步数超限、多少是参数填错、多少是检索没召回。

**不同原因对应完全不同的修法**：步数超限要改提示词或拆任务，
参数填错要改工具描述，检索没召回要改索引。

## 回归

每次改提示词或工具，都应该跑一遍固定的评测集。
没有回归集，你无法判断"这次改动是变好了还是变差了"——
很多优化是局部变好、整体变差。
