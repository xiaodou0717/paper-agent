# 上下文工程

## 为什么它比提示词工程更重要

提示词决定"模型怎么理解任务"，上下文决定"模型能看到什么"。

在 Agent 里，上下文是动态增长的：每一轮的工具结果都会追加进历史，
第 10 轮的输入可能是第 1 轮的十倍。不管理上下文，成本和延迟都会失控。

## 上下文膨胀的三个后果

1. **成本**：每轮重发完整历史，花费随轮次超线性增长
2. **窗口上限**：超过长度直接报错，任务硬失败
3. **注意力稀释**：长上下文里模型对中间内容关注度下降，答案悄悄变差（软失败）

第三点最难发现，因为它不报错，只是质量下降。

## 压缩策略

### 滑动窗口

只保留最近 N 轮。简单，但会丢掉早期的关键结论。

### 摘要压缩

把早期对话总结成一段话。损失可控，但摘要本身要花一次模型调用。

### 结构化提取

把关键事实抽成字段（已确认的需求、已完成的任务、待办事项），
丢掉原始对话。适合长任务。

### 检索替代

长文档不进上下文，放外部索引，用工具按需查。
这是 RAG 的核心思路，也是 Agent 处理大量资料时的标准做法。

## 分层设计

一个实用的分层：

- **常驻**：系统提示词、当前任务、关键约束
- **按需**：检索到的文档片段、工具返回值
- **可丢**：中间过程的思考、失败的尝试、重复的确认

判断标准是"丢了会不会导致下一步决策出错"。

## 观测

压缩是否有效必须用数据验证，不能凭感觉。要记录：

- 每轮的 `prompt_tokens` 变化
- 压缩前后的总 token
- 任务成功率有没有下降

只看"省了多少 token"是不够的。如果省了 40% 的 token
但成功率从 90% 掉到 60%，这个压缩就是失败的。
