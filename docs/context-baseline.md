## 二、静态成本：每轮都要付的固定开销

这一部分**与你走多少步无关**，是"挂上就付"的钱。

| 项 | tok | 说明 |
|---|---|---|
| 工具定义（2 个工具） | **482** | schema 791 字符，JSON 的 token 密度 0.64 |
| system 提示词 | 约 50 | |
| 每轮固定合计 | **约 530** | |

**换算参考**：如果挂 20 个工具，按每工具 240 tok 估，固定开销约 **4800 tok/轮** ——
在 4000 token 的上下文里就占 100% 以上。

## 三、动态成本：随轮数增长

### 3.1 短任务（3 步，W4 Day1/Day2 测）

| 轮 | 消息数 | 上下文 tok | 输出 tok |
|---|---|---|---|
| 1 | 1 | 551 | 204 |
| 2 | 5 | 1934 | 130 |
| 3 | 9 | 3830 | 1363 |
| **合计** | | **6315** | **1697** |

- 重发放大倍数：**1.65x**（累计输入 6315 / 最后一轮 3830）
- 分层（最后一轮）：工具结果 91%、工具定义 12.6%、tool_calls 4.6%

### 3.2 长任务（8 步，W4 Day4 测）

| 轮 | 消息数 | 上下文 tok | 输出 tok |
|---|---|---|---|
| 1 | 1 | 598 | 156 |
| 2 | 4 | 2076 | 408 |
| 3 | 9 | 3612 | 423 |
| 4 | 14 | 5120 | 650 |
| 5 | 18 | 6578 | 262 |
| 6 | 22 | 8181 | 350 |
| 7 | 26 | 9692 | 229 |
| 8 | 30 | 10975 | 235 |
| **合计** | | **57537**（输入+输出） | |

- 首末涨幅：**18.4 倍**（598 → 10975）
- 每步平均：**7192 tok**
- 完整任务需约 13 步 → 按此算法 **约 93000 tok**

### 3.3 增长规律

```
轮数 N，每轮上下文 ≈ 1500 × N（因为每轮新增一个工具结果）
总输入 ≈ 1500 × N² / 2
```

**成本是平方增长，不是线性。**

| N | 估算总输入 | 现实 |
|---|---|---|
| 3 | 6,750 | ✅ 轻松 |
| 8 | 48,000 | ⚠️ 接近普通预算上限 |
| 13 | 126,750 | ❌ 太贵 |
| 20 | 300,000 | ❌ 不可能 |

## 四、分层构成

### 4.1 短任务最后一轮（3830 tok）

| 层 | tok | 占比 |
|---|---|---|
| 工具结果 · read_doc | 1941 | 50.9% |
| 工具结果 · search_docs | 1529 | 40.1% |
| 工具定义 | 482 | 12.6% |
| 模型决策（tool_calls） | 175 | 4.6% |
| 用户输入 | 33 | 0.9% |

### 4.2 长任务最后一轮（7410 tok）

| 层 | tok | 占比 |
|---|---|---|
| 工具结果 · search_docs | 2507 | 33.8% |
| 工具结果 · read_doc | 1630 | 22.0% |
| **模型决策（tool_calls）** | **1104** | **14.9%** |
| 工具定义 | 482 | 6.5% |
| 用户输入 | 72 | 1.0% |

**关键差异**：`tool_calls` 从 4.6% 涨到 **14.9%**。

原因：模型每轮调 2~3 个工具，每次的 `arguments` 都存进历史。
8 轮 × 2~3 条 = 18 条，累积到 1104 tok。

> **短任务看不出这个问题。这就是必须在长任务上测的原因。**

## 五、退化现象（实测）

| 信号 | 预期（读文章得到的） | 实测 | 结论 |
|---|---|---|---|
| 重复调用增加 | 会 | **0 次**（18 次调用全不同） | ❌ 未出现 |
| 输出变短/敷衍 | 会 | **没变短**，后半反而更长 | ❌ 未出现 |
| 答非所问 | 会 | 没有 | ❌ 未出现 |
| 任务完成 | 会失败 | **budget，8 步停，无答案** | ✅ 出现 |

### 结论：**先撞成本墙，不是质量墙**

```
模型窗口（干扰发生处） ≈ 100 万 token
成本上限（普通预算）   ≈ 5~6 万 token

所以：先因为"付不起"停下（N≈8~13），
      还没来得及因为"变笨"失败（N≈50~100）
```

| 规模 | 主要矛盾 | 该做什么 |
|---|---|---|
| 3-5 步 | 几乎没问题 | 不用优化 |
| **8-13 步** | **成本** | 压缩、缓存、减层 |
| 20-50 步 | 成本 + 开始干扰 | 压缩 + 分层 + 摘要 |
| 100 步+ | **质量**（真·干扰） | 重构任务、多智能体 |

## 六、估算精度

| 场景 | 估算误差 |
|---|---|
| 短上下文（3 步） | -6.5% / +9.9% |
| **长上下文（8 步）** | **-21.8%** |

**误差随规模放大**：长上下文里 JSON 更多（tool_calls + 工具结果），
而 JSON 的 token 密度是近似值。

**影响**：`budget.py` 的 `SAFETY_MARGIN = 1.10` 在长任务里不够，
会低估 20% → 放行本该拦的调用。

**W5 待办**：把 `SAFETY_MARGIN` 提到 1.25，或对 JSON 密集上下文用更高系数。

## 七、压缩的现状

`budget.py` 目前只有一种策略：**截断最长的工具结果**（`per_result_limit`）。

实测压缩率曲线：

| 单条上限 | 压缩后 | 压缩率 | 每档多省 |
|---|---|---|---|
| 800 | 4106 | 8.3% | —— |
| 400 | 2575 | **42.5%** | +34.2 |
| 200 | 1771 | 60.5% | +18.0 |
| 100 | 1373 | 69.4% | +8.9 |

**400 是拐点**，再往下压边际递减明显。

**局限**：只能"截断"，不能"丢弃"。
早期轮次的工具结果（已经用过、模型不会再回头看）仍然占着位置。

## 八、W5 要验证的四条假设

| # | 假设 | 怎么验证 | 预期收益 |
|---|---|---|---|
| 1 | 滑动窗口（丢早期轮次）比截断更有效 | 同任务跑一遍，对比总 token | 省 40%+ |
| 2 | 摘要能省 token 但会丢细节 | 对比答案质量（人工判断） | 省 30%，质量下降 |
| 3 | 前缀缓存能显著降费 | 观察 `cached_tokens` 指标 | 费用降 50%+ |
| 4 | 工具定义按需加载是"白赚" | 挂 1 个 vs 2 个，对比固定开销 | 省 240 tok/轮 |

**验证方法统一**：跑同一个知识库审计任务（11 篇语料），
填上面各表的「W5 后」列。

## 九、这份基线怎么用

1. **W5 每做一个优化，就跑一次同一个任务**，把数字填进对应表格
2. **不要改任务 prompt**，否则数据不可比
3. 波动是正常的（模型每次调 1~3 个工具），**看趋势和量级，不抠绝对值**

> **没有基线的优化是自我感觉良好。**
> 这句话在 W10 做评测时会以另一种形式再出现一次。
